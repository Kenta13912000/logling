# Units：ログインとクラウド保存（account-sync）

## U-1：アカウント（`src/features/account/`）

- 含む Story：S-2, S-5, S-6
- 依存：U-2（ログイン・ログアウト・退会のあとに、どこのデータを表示するかを切り替える）

Google でのログイン・ログアウト・退会と、ログイン中のアカウントの画面（メールアドレス・ログアウト・退会）を受け持つ。「誰がログインしているか」を、ほかの Unit に知らせる。

## U-2：クラウド保存（`src/features/cloud/`）

- 含む Story：S-1, S-3, S-7
- 依存：
  - U-1（ログインしている人）
  - `src/features/home/`（保存データの形と読み書き。今はブラウザの中にだけ同期で読み書きしているので、ログイン中はクラウドに非同期で読み書きできるようにする）
  - `src/features/history/`（振り返りでの書き直し・削除・後から書く。保存先が変わっても同じ動きにする）

ログインしているかどうかで保存先（ブラウザの中・クラウド）を切り替え、読み込み中・読み込めなかった・保存できなかった、を画面に伝える。DB の表と、本人だけが読み書きできる決まりもここに置く。

## U-3：引き継ぎ（`src/features/migration/`）

- 含む Story：S-4
- 依存：U-1（初めてのログインを知る）、U-2（アカウントのデータを読み書きする）

初めてのログインで、ブラウザの中のデータとアカウントのデータを比べ、移す・選ぶ・確認するまでを受け持つ。

## U-4：説明ページ（`src/features/privacy/`、ページは `src/app/privacy/`）

- 含む Story：S-8
- 依存：なし（書く中身は、U-2 の ⑤ で決める DB・認証の ADR に合わせる）

何をどこに保存し、誰が読めるか、どう消せるかを説明する、ログインしなくても開けるページ。

S-9（スマホで使う）は、どの Unit の画面にもかかわるため、それぞれの Bolt で確かめ、最後の Bolt で一連の操作を通して確かめる。

### Bolt 計画

Unit をまたいで、土台から順に作る。

- Bolt-1：DB と認証の土台。DB・認証の ADR を作り、DB の表と、本人だけが読み書きできる決まりを作って、ほかのアカウントから読み書きできないことを確かめる（U-2。AC-29。ログインしていない人の分は Bolt-3）
- Bolt-2：Google でのログイン・ログアウトと、アカウントの画面（U-1。AC-2〜AC-6, AC-22, AC-24）
- Bolt-3：ログイン中はクラウドに読み書きする。読み込み中・読み込めなかった・保存できなかったときの扱い（U-2。AC-1, AC-8〜AC-12, AC-23, AC-29 のログインしていない人の分。AC-9 はほかの端末の代わりに、別のブラウザの状態で同じアカウントにログインして確かめる）
- Bolt-4：2 つの端末で同時に開いたときに、日記や経験値が二重にならない（U-2。AC-13）
- Bolt-5：ブラウザのデータの引き継ぎ（U-3。AC-14〜AC-21）
- Bolt-6：退会（U-1。AC-25〜AC-28）
- Bolt-7：説明ページと、そこへの入口。スマホ幅と、ログインから退会までの一連の操作の E2E テスト（U-4。AC-7, AC-30〜AC-32）

### 前提と順番の理由

- Bolt-1 の ⑤（ADR）は今すぐ作れるが、コードを書く ⑥ からは、Node 26 への更新（`fix/node-26`）を `main` に取り込んでから始める（ロードマップの約束。サーバーで動く処理を新しい Node の上で作るため）
- 本人だけが読み書きできる決まり（AC-29）は、日記を預かるうえでいちばん大事なので、画面より先に作って確かめる
- 2 つの端末で同時に開いたとき（AC-13）は、保存の仕組みの考え方が変わるため、ふつうの読み書き（Bolt-3）と分けて作る
- 説明ページは、書く中身が Bolt-1〜Bolt-6 で決まるため最後にする。Google ログインを一般に公開する前に必要になる見込み（⑤ で確かめる）

### 取り込みの依頼（PR）の分け方

- PR-1（ブランチ `feat/account-sync`）：①〜④ の文書と Bolt-1（DB と認証の土台）。画面は変わらない
- PR-2（ブランチ `feat/account-sync-app`。PR-1 を取り込んだ `main` から作る）：Bolt-2〜Bolt-7 と ⑧。本番の画面は、PR-2 を取り込むまで変わらない

### 設計（⑤で追記）

#### Bolt-1：DB と認証の土台

DB・認証の選定は [ADR-0005](../../adr/0005-db-auth-neon-better-auth.md)（Neon ＋ Better Auth ＋ Drizzle ORM。テストは PGlite）。

**ファイル**

```
drizzle.config.ts                         # drizzle-kit の設定（表の定義の場所と、SQL の出力先）
drizzle/NNNN_<名前>.sql                    # drizzle-kit で作った、表を作る SQL（リポジトリに残す）
src/lib/db/auth-schema.ts                 # Better Auth の表（user・session・account・verification）。Better Auth の CLI で作る
src/lib/db/schema.ts                      # logling の表（characters・diary_entries）と、auth-schema の書き出し
src/lib/db/test-db.ts                     # テスト用：PGlite の DB を作り、drizzle/ の SQL を当てて返す
src/lib/auth.ts                           # Better Auth の最小の設定（DB のつなぎ方だけ。Google は Bolt-2 で足す）
src/features/cloud/repository.ts / .test.ts  # 日記とキャラクターの読み書き。必ず「人の ID」を最初に取る
```

本番の DB へのつなぎ方（`@neondatabase/serverless`、秘密の値）は、実際に使い始める Bolt-2 で作る。Bolt-1 では本番の DB を作らず、画面も変えない。

**表**（Better Auth の `user` 表に、logling の 2 つの表をつなぐ）

| 表              | 列                                                                                                                                                                                                   | 守ること                                                                                           |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `characters`    | `user_id`（主キー。`user.id` を指す）・`name`・`total_exp`（0 以上）・`start_date`（日付。`diary-exp` のころのキャラにはないので空でもよい）・`created_at`・`updated_at`                             | 1 人に 1 体（主キー）。人を消すと消える（連鎖削除）                                                |
| `diary_entries` | `user_id`（`characters.user_id` を指す）・`date`（朝 4 時で区切った日付）・`body`・`created_at`・`written_later`（後から書いた印）・`bonus`・`bonus_days`（どちらも 1 以上。両方あるか、両方ないか） | 主キーは `user_id` ＋ `date`（1 人 1 日 1 件を DB で守る）。キャラクターを消すと消える（連鎖削除） |

列は今の保存データ（`SaveData`・`Character`・`DiaryEntry`）と 1 対 1 に対応させ、読み出すと同じ形の `SaveData` に戻せるようにする（Bolt-5 の引き継ぎで、レベル・連続日数・ボーナスが変わらないようにするため）。

**読み書きの関数**（`repository.ts`。どれも最初の引数が DB、2 つ目が「人の ID」）

| 関数                                      | すること                                                                                                         |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `getSaveData(db, userId)`                 | その人のキャラクターと日記を、今と同じ `SaveData` の形で返す（日記は古い順）。なければ `character: null`         |
| `createCharacter(db, userId, character)`  | その人のキャラクターを作る。すでにいれば何もしない                                                               |
| `insertEntry(db, userId, entry, exp)`     | その人の日記を 1 件足し、キャラクターの経験値を `exp` 増やす（1 つのトランザクション）。同じ日があれば何もしない |
| `updateEntryBody(db, userId, date, body)` | その人のその日の日記の本文を書き直す                                                                             |
| `deleteEntry(db, userId, date, exp)`      | その人のその日の日記を消し、経験値を `exp` 減らす（0 未満にはしない。1 つのトランザクション）                    |

- 結果は「できた」「その日の日記がない」「同じ日がもうある」「キャラクターがいない」のどれかで返し、画面での伝え方は Bolt-3 で決める
- 経験値の量（いつもの 10・後から書いた 5・ボーナス）をどこで計算するか（ブラウザかサーバーか）は、端末の時刻と朝 4 時の区切りにかかわるため、Bolt-3 で決める
- どの関数も SQL の条件に必ず `user_id = <人の ID>` を入れる。「人の ID」を取る関数は、ログインの情報から取り出したものだけを渡す（Bolt-2・Bolt-3 でサーバーの処理から呼ぶ）

**テスト**（`repository.test.ts`。PGlite の上で、本物と同じ SQL を当てる。jsdom ではなく Node の環境で動かす）

| テスト                                                             | AC           |
| ------------------------------------------------------------------ | ------------ |
| 人 A の日記とキャラクターは、人 B の `getSaveData` に出てこない    | AC-29        |
| 人 B は、人 A の日記の本文を書き直せない（A の日記は変わらない）   | AC-29        |
| 人 B は、人 A の日記を消せない（A の日記と経験値は変わらない）     | AC-29        |
| キャラクターのいない人 B は日記を足せず、人 A の経験値も変わらない | AC-29        |
| 足した日記・書き直し・消した結果が、`getSaveData` で同じ形に戻る   | AC-8（土台） |

「ログインしていない人からは読めない」（AC-29 の残り）は、サーバーの処理でログインの情報を確かめる Bolt-3 でテストする。

**入れる部品**

| 部品                   | 版                | 種類       | 用途                                          |
| ---------------------- | ----------------- | ---------- | --------------------------------------------- |
| `drizzle-orm`          | 0.45 系（安定版） | 本番で使う | 表の定義と読み書き                            |
| `better-auth`          | 1.7 系            | 本番で使う | 認証。Bolt-1 では表を作るための最小の設定だけ |
| `drizzle-kit`          | 0.31 系（安定版） | 開発だけ   | 表を作る SQL を出力する                       |
| `@electric-sql/pglite` | 0.5 系            | 開発だけ   | テストの DB                                   |

入れる前に、各部品の公式の手順と、Node 26・Next.js 16・Vitest 5 と組み合わせられるかを確かめる。Better Auth の CLI は、版を固定して使う（`latest` で毎回違う版を取ってこない）。

**Node 26 との順番**：⑥（テストを書く）からは、Node 26 への更新（`fix/node-26`）を `main` に取り込み、このブランチに取り込んでから始める。

## 判断メモ

- Units へのゲートでの判断：指摘なしで承認（本人だけが読める決まりを画面より先に作る順番も、このまま）
- PR の分け方：土台（Bolt-1）と、画面を伴う残り（Bolt-2〜Bolt-7）の 2 つに分けた。1 つにまとめると大きすぎ、Bolt ごとに分けるとログインの入口を隠す切り替えが要るため
- Bolt-1 ⑤ の作成前に確認した点：DB・認証は Supabase と Neon ＋ Better Auth を比べ、Neon ＋ Better Auth にした（ADR-0005）
- Bolt-1 ⑤ へのゲートでの判断：指摘なしで承認（RLS は重ねない、ログインしていない人のテストと経験値の計算の場所は Bolt-3 で決める、ADR-0001 と README へのリンクは ⑧ で直す、もこのまま）。⑥ は Node 26 を取り込んでから始める
- Bolt-1 ⑥ へのゲートでの判断：指摘なしで承認。設計の表にない、保存の形を確かめるテスト（ボーナス、始めた日のないキャラクター、1 人 1 体、経験値が 0 より下がらない）と、AC-13 の土台（同じ日を二重にしない）のテストを足した
