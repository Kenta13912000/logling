# ADR-0007：書き忘れのお知らせの送り方（Web Push と、定期的に確かめるしくみ）

- 日付：2026-11-13
- 状態：採用

## 背景

`pwa-reminder` の U-2 で、ログインしている人が「設定」でオンにした端末に、選んだ時刻（30 分ごと）に、まだ書いていない日だけお知らせを送る（[intent.md](../aidlc/pwa-reminder/intent.md)・[stories.md](../aidlc/pwa-reminder/stories.md)）。そのために、次のことを決める必要がある。

- お知らせを端末に届けるしくみと、サーバーで使う部品
- 「いま送る時刻か」を定期的に確かめるしくみ（Vercel の無料プラン（Hobby）で動くもの）
- 端末への宛先（ブラウザが作る「この端末に送ってよい」という情報）の保存のしかたと、守り方

## 決定

### 届けるしくみ：Web Push（VAPID）と `web-push`

- ブラウザの標準の Web Push を使う。ブラウザが作る宛先（Apple・Google などのお知らせのしくみのアドレスと、暗号の鍵）を DB に保存し、サーバーがそこへ、暗号にしたお知らせを送る
- サーバーの身元を示す鍵（VAPID の鍵の組）を 1 つ作る。公開の鍵はブラウザに渡し、秘密の鍵は Vercel の環境変数（Production だけ・Sensitive）と手元の `.env.local` にだけ置く。鍵の持ち主の連絡先（`subject`）には、個人のメールアドレスではなく、GitHub の Issues のページ（`https://github.com/Kenta13912000/logling/issues`）を使う
- お知らせの暗号化と署名は、部品 `web-push`（4.0.0、MPL-2.0。Web Push の参照実装として広く使われている）に任せる
- お知らせの中身は、題「logling」と文（キャラクターの名前と決まった文）、押したときに開く `/` だけ。日記の本文は入れない

### 定期的に確かめるしくみ：Vercel Schedules（試験提供）

- `vercel.json` の `schedules` に、`/api/reminders` を 30 分ごと（`0,30 * * * *`）に呼ぶ予定を書く（`path` の呼び先）。Hobby では毎回 0〜15 分ずれ、ひと月に 5,000 回までのところ、約 1,440 回使う
- `/api/reminders` は公開の入口になるので、Vercel が送る合言葉（`CRON_SECRET`。16 文字以上の乱数）を、時間で差が出ない比べ方で確かめ、違えば何もしない
- 同じ回が 2 回届くことがあるため、宛先ごとに「最後に送った日」を記録し、同じ日には 2 回送らない（AC-13）

### 宛先の保存と守り方

- 宛先は、ログインしている人のアカウントに結びつけて、端末ごとに 1 行で保存する（表 `push_subscriptions`）。退会すると、アカウントと一緒に消える
- 受け付ける宛先のアドレスは、`https` で、知られているお知らせのしくみのものだけにする（Apple：`*.push.apple.com`、Google：`fcm.googleapis.com`・`android.googleapis.com` の 2 つだけ（`googleapis.com` の下にはほかのサービスもあるため、名前を決め打ちにする）、Mozilla：`*.push.services.mozilla.com`、Microsoft：`*.notify.windows.com`）。好きなアドレスを登録できると、logling のサーバーにそこへ通信させられてしまう（SSRF）ため
- 宛先の持ち主は、サーバーのログイン情報から決める。ブラウザから送られてきた人の ID は使わない（`account-sync` と同じ）

## 検討した他の案

| 案                                                                          | 採らなかった理由                                                                                                                                             |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| お知らせの会社のサービス（OneSignal・Firebase Cloud Messaging の SDK など） | 外部のスクリプトを読み込むことになり、「ページのスクリプトはすべて同じオリジンから」（`release` AC-9）に反する。宛先や時刻を、ほかの会社にも預けることになる |
| 暗号化と署名を自分で書く                                                    | 間違えると届かない・安全でない。参照実装の部品に任せる方が確か                                                                                               |
| Vercel の Cron Jobs                                                         | Hobby では 1 日 1 回までで、最大 59 分ずれる。一人ひとりの時刻に合わせられない                                                                               |
| Vercel Pro にする                                                           | 1 分ごとに動かせるが、費用がかかる。30 分ごとで十分                                                                                                          |
| GitHub Actions の定期実行                                                   | 無料だが、混んでいると数十分遅れることがあり、時刻が読めない。合言葉を GitHub にも置くことになる。Schedules が使えなくなったときの代わりの案として残す       |
| 外部の定期実行サービス（cron-job.org など）                                 | 合言葉をほかの会社に預けることになる                                                                                                                         |
| Schedules の `function` の呼び先（公開されない関数）                        | 合言葉が要らず安全だが、Next.js の App Router の中の処理を呼び先にする方法が、試験提供の段階でははっきりしない。`path` と合言葉で十分守れる                  |

## 結果・影響

- 部品 `web-push` が増える（サーバーでだけ使う）
- 環境変数が増える：`NEXT_PUBLIC_VAPID_PUBLIC_KEY`・`VAPID_PRIVATE_KEY`・`CRON_SECRET`。本番は Vercel の Production に、手元は `.env.local` に置く。PR ごとの確認用の公開には置かない（ログインがないため、お知らせも使えない）
- 表 `push_subscriptions` が増える。PR-2 を取り込む直前に、本番の DB に当てる
- Schedules は試験提供のため、条件が変わることがある。使えなくなったときは、GitHub Actions の定期実行に切り替える（呼び先と合言葉はそのまま使える）
- お知らせは、Apple・Google などのお知らせのしくみを通って届く。説明ページにそのことを書く（AC-19）
