# ADR-0004：Node.js を 26（LTS）に上げる

- 日付：2026-11-11
- 状態：採用（[ADR-0001](0001-tech-stack.md) の「実行環境」を置き換え）

## 背景

[ADR-0001](0001-tech-stack.md) では、実行環境を Node.js 24.22.1 にし、手元（`.nvmrc`）・CI・Vercel（`package.json` の `engines.node`。[ADR-0003](0003-hosting-vercel.md)）でそろえた。その後、次のことがわかった（公式の情報、2026-11-11 時点）。

- Node 26 は 2026-10-28 に LTS（長く支える版。名前は Lithium）になった
- Node 24 は 2026-10-20 に「保守のみ」の期間に入った。重大な修正だけが出る。サポートは 2028-04-30 まで
- Node 26 は 2027-10-20 まで活発に修正され、サポートは 2029-04-30 まで
- Vercel で使える版は 26（標準）・24・22。決められるのは大きい版の番号だけで、細かい修正版は Vercel が自動で当てる
- 2026-11-11 に、22・24・26 系そろって安全のための修正版が出る予定（最も重い問題は「高」）

次の機能 `account-sync` では、ログインや DB への読み書きなど、サーバーで動く処理が初めて入る。その前に Node を新しい LTS に上げ、新しい Node の上で作りたい。

## 決定

- Node.js **26.13.0**（今ある 26 系の最新）に上げる。予定の安全のための修正版が出たら、手元と CI を小さな作業で上げ直す
- `.nvmrc` を `26.13.0` にする。CI は `.nvmrc` を読むので、自動でそろう
- `package.json` の `engines.node` を `^26.13.0` にする。Vercel は 26 系の最新を使う（`^` にするのは、「以上」の指定だと次の大きい版を使うおそれがあるため。ADR-0003 と同じ考え方）
- `@types/node` を、実行環境に合わせて 26 系にする（ADR-0001 の補足の判断と同じ考え方）
- 手元の Node は、公式サイトの Windows 用インストーラーで入れ替える（バージョンを切り替える道具は使っていない）
- 3 か所がそろっていることを、単体テストで確かめる（`src/app/runtime-config.test.ts`）
  - `engines.node` が `^` ＋ `.nvmrc` の版であること（もとからあるテスト）
  - `.nvmrc` が 26 系であること
  - テストを動かしている Node が、`.nvmrc` と同じ大きい版であること（手元の入れ替え忘れに気づくため）

## 検討した他の案

| 案                                   | 採用しなかった理由                                                                                                                                                                                                                                                     |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Node 24 のまま使う                   | 2028 年 4 月まで使えるが、すでに「保守のみ」の期間に入っている。`account-sync` でサーバーの処理を作ったあとに上げると、確かめる範囲が広くなる                                                                                                                          |
| 安全のための修正版を待ってから上げる | 待てば上げ直しが 1 回で済む。ただし、直される弱点は今の 24.22.1 にもあり、26.13.0 に上げても危なさは変わらない。本番（Vercel）は修正版が出れば自動で当たり、手元と CI は外からつながれる場所ではない。待つより、`account-sync` を Node 26 の上で早く始めることを選んだ |
| `engines.node` を `26.x`             | Vercel では同じ結果になるが、手元・CI と同じ版を下限にする今の形（`^` ＋ `.nvmrc`）とテストをそのまま使えるため、`^26.13.0` にした                                                                                                                                     |

## 結果・影響

- 手元・CI・Vercel が Node 26 にそろう。Vercel では、26 系の細かい修正版が自動で当たる
- 手元の Node を入れ替えたら、`npm ci` で部品を入れ直す
- 安全のための修正版が出たら、`.nvmrc` と `engines.node` をその版にし、手元の Node を入れ替える（軽い手順の小さな作業）
- ADR-0001 の「実行環境」の行と、ADR-0003・要件定義書（`release`）にある `^24.22.1` を、この ADR に合わせて直す
- 次の大きい LTS に上げるときも、`.nvmrc` と `engines.node` を変え、テストの「26」を直す

## 判断メモ

- 作成前に確認した点：「v22 以上」の条件は Node 24 で満たしていたが、そのうえで 26 に上げる
- 変えた点：はじめは 11/11 の安全のための修正版を待って 1 回で上げる予定だったが、11/11 の時点でまだ出ていなかった。26.13.0 が今の 24.22.1 より危なくなるわけではなく、本番は修正版が自動で当たるため、26.13.0 で上げることにした（開発者の判断）
- ゲート 3 での判断：指摘なしで承認。修正版への上げ直しと、入れ直しのときに見つかった ESLint 9 のサポート終了への対応は、ロードマップの「機能以外の作業」に書いた
